# 2026.277.0738 — feat(command): carry captured stdout on the PASS result

## Summary

`command:command` computed a step's stdout, matched it, and then **threw it away**. `RunVerb`'s PASS arm returned a bare `kit.Passf("exit=%d", exitCode)`, so the bytes existed only long enough to satisfy `stdout:`/`stderr:` matchers. Nothing downstream could read them.

That is the missing half of the workflow hand-off. A lobster step reads the previous step as `$id.stdout` / `$id.json`, and in charly the equivalent is a plan step reading the previous step's result — but `CapturedValue` had **no producer anywhere in the org**. `verb.RunVerb` returns `spec.CheckVerbResult` (`spec/checkcontext.go:163`; `kit.Result` is a plain alias for it — `sdk/kit/kit.go:83`), and charly converts it to its internal `spec.CheckResult` (`cue_types_gen.go`, from `#CheckResult`) at the dispatch boundary. Both carry `CapturedValue`; before this change **neither was ever assigned**:

So the pre-change producer count was zero, and the only reader anywhere was plugin-task's. `charly task --output` was therefore correct by construction and inert in practice — `printCapturedValue` prints *nothing* when the value is empty ("An absent step or an empty value prints NOTHING (a successful run still exits 0 — never a placeholder)"), so the flag reliably emitted 0 bytes.

This change makes `command:command` the producer.

| change | file | why |
|---|---|---|
| **PASS results carry the captured stdout** | `plugin.go` | the PASS arm now sets `res.CapturedValue = stdout` instead of discarding it, so a downstream step can consume this step's output. |
| **Bounded at 1 MiB, truncation NAMED** | `plugin.go` | `maxCapturedStdout = 1 << 20`. Output over the cap is stored truncated to exactly the cap **and the truncation is written into `Message`** (`exit=N; stdout truncated to 1MiB of M bytes`). A silently shortened value is a fake the consumer cannot distinguish from the real output, so the clip is visible. The `exit=` prefix is preserved so anything keying on it still matches. |
| **PASS ONLY** | `plugin.go` | the `Failf`/`Skip` returns above are untouched and leave `CapturedValue` empty **on purpose**. A failed step's output was never vouched for; a consumer that read it would be acting on a value the step itself rejected. |

Net: **+23/-1 in `plugin.go`, +68 in `plugin_test.go`.**

**Consumer obligation, stated because it is invisible in the diff — and it is TWO prerequisites, not one.** This is the *producer* leg, and a producer alone is not enough; the value has to survive the host's dispatch too. `charly task --output` (opencharly/plugin-task#9) reads it, and both of these must hold before it prints anything:

1. a charly build that compiles in a `plugin-command` at or after this change's tag — `charly` pins `plugin-command v0.2026272.26` today, which predates it; **and**
2. a charly at or after the `CapturedValue` dispatch fix (a `charly fix(check): carry a verb's CapturedValue through EVERY dispatch path` commit on the `feat/workflow-ir` branch, issue opencharly/charly#780 for the still-open out-of-process half).

(2) is not a formality, and it is why this PR's own bed is worth reading: with this producer compiled in but the charly fix absent, the `check-task` bed's `task-output-captured` step still measured `stdout: expected to contain "TASK-SMOKE-OK" (got: )` — four charly dispatch paths each built their result from the verb's verdict without copying the field. The producer was correct and unobservable at the same time. Both halves are named here so the consumer requirement is not understated by a diff that cannot show it.

**Blast radius, stated because it is a real behaviour change and not only an addition:** `command:` is one of the most-used verbs, so this now makes **every passing `command:` step** carry up to 1 MiB of stdout in the check-run ledger where it previously carried nothing. The field is `omitempty`, so a step that captures nothing stays byte-identical to before; a step that passes *and prints* rides its output, bounded by the 1 MiB cap. If the org judges that cost too high for verbs that never wanted a capture, the answer is the opt-in `capture:` op field the stale comment describes — which is a spec-wide contract change (spec + charly threading + every consumer), filed as `opencharly/spec#194` rather than smuggled in here. **That no such op field exists is a sweep, not a recollection — §4 ships its command and its output.**

### The overlay, stated because it is what makes this run possible

The bed needs a charly that compiles this plugin in, and the pin that would do that can only adopt a tag that does not exist until this merges. So the binary is built the documented Go-`replace` way — the mechanism `/charly-check:check`'s `beds-and-r10.md` names as the *"Go-`replace`-style 'verify before you push'"* dev-tree override:

```
go build -o ./bin/charly \
  -ldflags "-X main.BuildCalVer=$(bash scripts/calver.sh)" \
  -replace github.com/opencharly/plugin-task/candy/plugin-task=<worktree>/candy/plugin-task \
  -replace github.com/opencharly/plugin-command/candy/plugin-command=<worktree>/candy/plugin-command \
  ./charly
```

`go.mod`/`go.sum` are snapshotted before the build and restored after it, so the worktree is clean and carries no replace directive. `plugin-command` is compiled in (`charly.yml`, `compiled_plugins:`), so this bed takes the **in-proc** dispatch path and compiles the changed producer in; `plugin-task` likewise.

**This bed does not run green against `origin/main`'s pins, and that is expected — the 8-step `check-task` exists only with all three legs in the module graph.** `charly`'s `main` today carries a 2-step `check-task` (`task-list-declared`, `task-verb-runs`) that touches neither `--output` nor stdin, so **merging this PR reddens no existing gate**; the six further steps (including `task-output-captured`) are added by the charly leg. Nothing *shipped* therefore certifies this PR's surface at its own merge state — that certification is the charly leg's, which runs the full bed last.
