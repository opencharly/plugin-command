# 2026.297.1448 — feat(command): give a `command:` step the org's "the phase ran nothing" channel

Closes #10

## Summary

The org already owns the vocabulary for "the phase ran nothing" — `sdk.CheckSkippedExitCode = 3` (`github.com/opencharly/spec/exitcode`: *"the phase RAN NOTHING — neither a pass nor a failure"*) — and plugin-check's bed runner already honours it (`candy/plugin-check/no_plan_skip.go:52`: a bed step whose child exits 3 is recorded as skipped, with its reason).

The `command:` verb was the one place the convention could not reach. Its exit-code contract is `{0, exit_status}` plus the `expect_non_zero` arm, so a step whose script reports "nothing ran" with the org's own code had exactly one possible reading: **failed**. This PR gives the verb the third state.

`#CommandInput` — the plugin's OWN schema, plugin-exclusive by construction — gains `skip_exit?: int`:

```yaml
- check: the gate that may have nothing to compare
  command:
    command: scripts/check-foo.mjs
    skip_exit: 3
```

A command that exits the declared code is **SKIPPED**: neither a pass nor a failure, and the stdout/stderr matchers do not run for it (a step that ran nothing has no output to assert on).

**The declaration is validated, not trusted**, and it is checked BEFORE the command runs, so an authoring error never runs a probe:

- only the org's code is accepted (`sdk.CheckSkippedExitCode`); a private code is refused with a message naming the org's, so "3" cannot mean two things across the org;
- a declaration contradicting the step's own `exit_status` — the SAME code — is refused rather than silently overriding it: one code cannot be both the pass and the skip;
- `background: true` is refused: a backgrounded command has no exit status to interpret, so a skip code declared there would be silently inert.

**The precedence is stated, not left to be discovered.** The skip is read first, so a step declaring `skip_exit` together with `expect_non_zero` means "exit this code → skipped; any other non-zero → passed" — a wildcard narrowed by an exact exception. Only an exact-code contradiction is refused.

**It is OPT-IN, deliberately** — an explicit deviation from opencharly/plugin-task#35's unconditional wording, stated on that issue and here. Two measured facts make the unconditional rule unsafe at this layer:

1. it would swallow two existing assertions — `exit_status: 3` is a PASS expectation, and `expect_non_zero: true` is a "must fail" expectation; a step that ASSERTS an exit code would stop asserting it;
2. the exit code belongs to the step's AUTHOR, not to the verb: a `command:` step runs an arbitrary shell script, not a charly-driven phase, so an undeclared 3 is an authoring error, not a phase report. Reading it as a skip turns a real failure into a non-failure.

The shared `#Op` `exit_status` matcher is not overloaded — it is a base field read by the command, http and live-probe verbs alike.
