# 2026.297.1452 — test(command): make the background-guard case discriminate the guard

Closes #10

## Summary

The org's validator read the merged PR #11 and raised two observations. This PR dispositions the one that is a defect, and records the other.

**The defect: a test that could not fail.** `TestCommandVerb_SkipExitWithBackgroundIsRefused` was absent from the red control's list — with the guard removed, the case still passed. The reason is mechanical: the pre-existing background refusals (`"background: true is host-side only"`, `"background command not meaningful under charly check box"`) also say **"background"**, which is the word the assertion checked. So the case asserted a status and a word that the code produced with or without the guard, and the guard itself was covered by nothing.

R7: *a test that cannot fail is invalid*. The assertion now names **`skip_exit`**, which only the guard's own message carries, and the case is split into the two variants that behave differently without it:

- **in-container** (`background: true`, default `in_container: true`): without the guard the verb fails on the pre-existing "host-side only" refusal, so the message is what discriminates.
- **host-side** (`background: true`, `from_host: true`): without the guard the verb **PASSES** (`"backgrounded pid=…"`) — the declaration is silently inert, which is exactly what the guard exists to prevent. With the guard, nothing is started at all.

The change is test-only: no runtime behaviour moves.

**The record: the count.** PR #11's body said the diff adds "ten cases" of the verb's own; it adds **eleven** (nine fake-driven, two live). The body is corrected in place, and this PR's body — which becomes the next `CHANGELOG/` entry — records the correction, because the published `CHANGELOG/2026.297.1448.md` and the squash commit's message still carry the word "ten". Both are written by the merge-time workflow and are not hand-edited here: the changelog belongs to the workflow, and a merged commit's message is history.
